# Motion Workbench 2.0 · Phase 3 变更报告（Motion Recipe 组合系统）

> 目标：把「组合方案」从一份成员清单，做成**看得懂、能逐步检查、能按顺序预览**的配方。
> 本阶段把内置组合从 5 套扩到 **30 套（119 步）**，每一步都带 **作用 / 所在层级 / 可调参数 / 性能成本**，
> 并在工作台里加了「组合模式」面板与「依次预览」。

---

## 一、这一阶段交付了什么

| # | 交付物 | 说明 |
| --- | --- | --- |
| 1 | **组合步骤模型** | `motion_recipe.steps`：`[{templateKey, stage, role}]`，按应用顺序；`stage` 是这一步负责哪一层，`role` 是它的作用 |
| 2 | **30 套内置组合** | 5 套既有方案补上步骤 + 25 套新方案；共 **119 步**，覆盖六个场景 |
| 3 | **步骤接口** | `GET /motion/templates/recipes/{recipeKey}` 与列表接口都返回 `steps` 与 `performance` |
| 4 | **整体性能成本** | 最重档位 + 三档各占几步 + 一句降级建议（点名到具体某一步） |
| 5 | **组合模式面板** | 工作台里点开一套方案：每一步显示 **动画 / 作用 / 参数 / 性能成本**，点某一步就把舞台切到那一步 |
| 6 | **依次预览** | 按步骤顺序每 4.2 秒自动往下走一步，走完自动停；手动点步、切换方案、离开页面都会停 |
| 7 | **生成器** | `_gh/mr_build.py` + `_gh/mr_data.py`：校验引用的模板真实存在、按服务端口径算分数、生成幂等种子 |

## 三、数据

| 项 | 内容 |
| --- | --- |
| 结构变更 | `motion_recipe.steps LONGTEXT`（`db/extensions_motion_recipe.sql`，information_schema 守卫，可重复执行） |
| 建表同步 | `db/extensions_motion_template.sql` 的 `CREATE TABLE motion_recipe` 里也补了这一列，全新安装一步到位 |
| 种子 | `db/extensions_motion_recipe_seed.sql`（30 套 / 119 步），按 `recipe_key` upsert，重跑不产生重复 |
| 分数口径 | 生成器与服务端用同一套权重（视觉 30 / 代码 25 / 复用 25 / 性能 20）算成员均值，库里那列只是缓存 |
| 引用校验 | 生成器会先校验每个 `templateKey` 真实存在，引用了不存在的模板直接生成失败（不写悬空引用） |

**没有新增任何模板**：30 套方案全部由已有的 60 个模板（官方 30 + 社区 30）组合而成，
其中 55 个模板被至少一套方案用到（60 个模板里有 55 个进了至少一套组合）。这也说明组合这一层是**真的在复用已入库的动效**，而不是又造一批新素材。

## 五、两个设计取舍

**一、整体性能成本取「最重的一步」，不取平均。**
一个方案里只要有一处是 GPU 档，平均值就会把这件事抹平，而用户真正要判断的是「跑到那一步会不会卡」。
所以最重档位单独给出，降级建议点名到具体那一步 —— 例如「最重的一步是『粒子星网』，移动端可以把它换成同场景的轻量模板，其余步骤照旧」。

**二、`memberKeys` 只放真的有模板的成员。**
它要与 `members`、`steps` 一一对应，否则界面会出现「5 个动效」却只列出 4 步的矛盾。
找不到的成员仍然会记日志，但不再混进成员清单。
